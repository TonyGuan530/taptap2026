C 是“借助现有物体和动量改造地形”。

如果真人真的能在同一关里自然地产生这三种思路，那么这个 mechanic 就已经开始具备真正的 toy 感。

尤其 C 很重要。因为它意味着玩家不是只在问：

“哪个词条可以直接解决沟？”

而可能开始问：

“场景里这些东西还能被我怎么利用？”

最大问题

现在最大的风险已经不是“属性克制”。

已经变成：

系统有涌现能力，但玩家可能看不懂、想不到，最终仍然只使用最显眼的一条解法。

这是一个 discovery / affordance 问题。

如果 10 个玩家里 9 个都用 Float 长板搭桥，另外两套系统解虽然技术上存在，但玩家从不想到，那么从体验角度它仍然会退化成：

“有隐藏多解的标准谜题”

而不是：

“玩家在系统里发明解决办法的 toy”。

这也是你问的第二个问题的核心。

自动化验收对“涌现”最大的盲区

你们现在的“几何断言 + 实机通关”非常适合验证四件事：

解法在物理上真的成立；
参数没有悄悄被改坏；
某条路径不是理论可行而实际不可操作；
后续修改没有破坏已有 solution space。

这套自动化应该保留。

但它对涌现有至少 6 个关键盲区。

第一，不会测玩家是否想得到。

测试知道答案，所以它验证的是：

solution feasibility

真人试玩要验证的是：

solution discoverability

这是目前最大的盲区。

第二，不会测玩家是否理解因果。

玩家可能偶然把 Sticky 方块扔下去，恰好过去了，但不知道为什么成功。

这种情况 technically 是通关，但不是 mechanic learning。

真正想要的应该是玩家能形成可迁移模型：

“Sticky 接触一段时间后会固定，那我以后可以拿它做支撑。”

第三，不会发现设计者没想到的解。

现在测试的是 A/B/C。

但对“涌现”最有价值的数据，反而是：

D：测试者自己找到一种你们没列出来的打法。

自动化基本不可能主动发现这种情况，除非以后专门做 search/fuzzing agent；GameJam 阶段也没必要。

第四，不会测解法是否存在明显 dominance。

理论上三解都成立，但实际可能：

Float：3 秒，稳定，零风险；
Sticky：15 秒，需要精确操作；
Heavy：20 秒，经常失败。

那从真人体验上，其实只有一个“实际答案”。

这属于 solution viability，不只是 feasibility。

第五，不会测 experimentation cost。

涌现类玩法很依赖：

尝试 → 看结果 → 修正 → 再尝试。

如果每次失败要重来 30 秒、墨水浪费太狠、对象掉沟后无法快速恢复，那么系统再丰富，玩家也不会愿意实验。

自动测试通常不会感受到这种 friction。

第六，不会测“意外但合理”的主观感受。

一个 emergent outcome 之所以有趣，通常需要同时满足：

我没预料到 + 但发生后我理解为什么。

如果结果完全不可预测，就是 chaos。

如果完全可预测，就是工具使用。

自动测试只能确认 deterministic / physical correctness，无法确认这个心理区间。

下一版建议

这里我建议非常明确：

先不要继续加系统。先做人测。

而且不是泛泛地“找人试玩看看”，而是做一次很小的、带观察指标的 blind playtest。

第一条，直接把 L3 给 5～8 个没有参与开发的人玩。不要告诉他们“三种解”，也不要解释哪种词条该怎么用，只给每个词条一句基础定义。

记录四个数据：

第一成功解法；
第一次通关耗时；
尝试过哪些组合；
有没有出现你们没预设的打法。

最重要：录操作过程，不要只收口头评价。

第二条，给系统加一个非常轻量的 telemetry/debug log，不需要后台。

每局本地记录：

timestamp / shape / tag / spawn_position / ink_cost / object_contact / death_or_reset / goal

最后导出 JSON 或直接 console log 都行。

这样你们可以回放：

玩家什么时候第一次试 Heavy？
Sticky 被尝试过没有？
他试了 8 个组合还是一眼搭桥？
成功前经历了几次有意义的实验？

这比“好不好玩 1～5 分”有用得多。

第三条，暂时不要改 L3，除非测试暴露明显 usability blocker。

这一点很重要。

不要在真人测试前再加 Water、Bounce、Grow，也别加 SIZE。

因为现在已经终于有了一个可用于测假设的干净实验场。

如果你继续修改，反而会污染这次 Gate 的结果。

不建议现在做

仍然不建议：

加新词条；
做真正自由画图；
做更多关卡；
做正式美术；
加复杂教程；
为 A/B/C 分别做成就或提示；
在关卡里提示“这里有三种解”。

尤其最后一点不要做。

你现在最需要知道的就是：

玩家在完全不知道“三解存在”的情况下，会不会自行展开搜索。

所以不要提前教育他们这个关卡“是多解的”。

当前结论

KEEP

这次我会把 v1 的 ITERATE 提升到 KEEP。

不是因为“28 项 PASS”。

而是因为上一轮需要验证的核心结构性假设已经过关：

当关卡去掉显式属性锁，只保留统一物理规则和一个终局目标时，现有 4 词条 × 3 形状仍然能够自然提供多条不同物理关系的有效路径。

这足以说明这个 mechanic 值得继续占用 GameJam 的试玩验证时间。

但这个 KEEP 的含义是：

核心系统值得保留，下一阶段应该验证真人行为。

不是：

继续堆功能。

下一道 Gate 我会定义成真人数据 Gate：

在不给解法提示的情况下，至少有部分玩家主动尝试超过一种系统关系；不同玩家产生不完全相同的解法路径；最好至少出现一次开发者未明确预设的合理解法。

如果最终所有人都稳定收敛到 Float 长板桥，那 mechanic 仍需要迭代；如果解法开始自然分叉，甚至出现 D 解，那么 demo-06 就真正从“系统上支持涌现”进入“玩家体验中发生涌现”。
